# v0.13 — Internal Hardening — Design

*Status: approved design · 2026-06-30*
*Theme: stability & operability over new intel (Horus is internal-only)*

---

## 1. Context & Goal

Horus is at `0.12.0`. Two roadmap threads ran in parallel and tangled at the
version number:

- **"Exposure & Prediction"** (the v0.11 spec): M1 (EPSS history+velocity) and
  M2 (imminence forecast) shipped; M3/M4/M5 did not.
- **"Modular/Deployable/Configurable"** (the v0.12 audit): docker-compose,
  `deploy.sh`, healthcheck, source toggles, security hardening — landed
  (incl. the 2026-06-30 docker `.env`-optional fix + `--update` DB backup).

v0.13 deliberately does **not** open a new intel frontier (correlation,
verification, ATT&CK, STIX). It hardens what exists for reliable internal
production use. Four workstreams: two continuous quality sweeps (foundation),
two scoped features built on top.

```
Foundation (first, continuous):
  A. mypy --strict expansion      B. coverage gate → 80% (target 85%)
Features (on the hardened base):
  C. source health visibility     D. KEV due-dates (M3) + API docs
```

Sequencing rationale: tightening types/tests first means C and D land on
already-clean layers (e.g. `enrichers/` and `notifications/` get typed right
before M3 modifies them).

### Non-goals (explicitly deferred)

- Runtime source toggle/credential UI (the audit's D2.1 full panel) — would
  fight the env-based `HORUS_SOURCES_ENABLED` model. The admin page is
  **read-only**.
- M4 (Shodan exposure) and M5 (ML outcome logging) — remain in the
  Exposure & Prediction backlog, not v0.13.
- Postgres / async pipeline / multi-worker scaling.

## 2. Workstream A — mypy `--strict` expansion

### Current state
Strict scope in `pyproject.toml` `[[tool.mypy.overrides]]` already covers:
`horus.core.*`, `horus.pipeline`, `horus.storage.db`, `horus.storage.query`,
`horus.storage.backfills`, `horus.net.http`, `horus.net.auth`.

### Design
Expand strict coverage layer by layer, in dependency order. Each layer is its
own commit that (1) fixes annotations in that layer and (2) adds the module
glob to the strict override list. The CI mypy gate moves with each commit.

Order (least→most dependent on app context):

1. `horus.storage.*` (remaining: schema helpers, migrations)
2. `horus.enrichers.*`
3. `horus.sources.*`
4. `horus.notifications.*`
5. `horus.config.*`
6. `horus.bot.*`
7. `horus.render.*`
8. `horus.web.*` (largest; last)

### Acceptance
- `mypy` passes strict on every layer listed above.
- CI runs `mypy` and fails on any strict error in covered modules.
- No `# type: ignore` added without an inline reason comment.

## 3. Workstream B — coverage gate → 80%

### Current state
610 test functions, 74.5% line coverage, pytest-cov gate at 70%.

### Untested modules (priority targets)
- `horus/notifications/dispatcher.py` — notification routing/dispatch
- `horus/bot/telegram.py` — bot command handlers, markdown escaping
- `horus/config/` — `.env` parsing (existing env wins, quote stripping),
  source discovery
- `horus/net/xsearch.py` — X/Twitter auth flow / query building

### Design
Add focused unit tests for the four modules above (mock external I/O:
Telegram API, Chrome cookie store, filesystem). Once line coverage clears
80%, raise the enforced `--cov-fail-under` gate to **80%** in `pyproject.toml`
and CI. 85% remains the stretch goal but is **not** enforced (headroom so a
marginal-coverage run doesn't block unrelated PRs).

### Acceptance
- The four modules have meaningful behavioral tests (not just import smoke).
- `pytest --cov` reports ≥80% overall; gate set to 80% and green in CI.

## 4. Workstream C — source health visibility

### Problem
All sources run every cycle; failures are only visible by reading logs. There
is no at-a-glance "which sources are working" view. The pipeline already
tracks per-source *scheduling* (`db.get_last_run` / `db.mark_run`,
`pipeline.py:198,352`) and each source's `run(ctx)` already returns a result
dict (`pipeline.py:227`) — health is an extension of an existing hook, not new
plumbing.

### Data model
New table `source_health` (one row per source, upserted each cycle):

| Column                  | Type    | Notes                                  |
|-------------------------|---------|----------------------------------------|
| `source_name`           | TEXT PK | matches discovered source module name  |
| `last_run_at`           | TEXT    | ISO-8601 UTC                           |
| `last_status`           | TEXT    | `ok` \| `error` \| `skipped`           |
| `last_error`            | TEXT    | error message, NULL on success         |
| `cve_count`             | INTEGER | CVEs returned last run                 |
| `poc_count`             | INTEGER | PoCs returned last run                 |
| `consecutive_failures`  | INTEGER | reset to 0 on `ok`, increment on error |

`skipped` = source not in `HORUS_SOURCES_ENABLED`. The existing `last_run`
marker stays for scheduling; `source_health` is observability only.

### Pipeline hook
Wrap the existing `mod.run(ctx)` call (`pipeline.py:227`) in try/except:
- success → upsert `last_status='ok'`, counts from result dict,
  `consecutive_failures=0`.
- exception → upsert `last_status='error'`, `last_error=str(e)`,
  `consecutive_failures += 1`, and **continue the cycle** (one bad source must
  not abort the run; preserve current behavior).
- disabled source → upsert `last_status='skipped'` (so the UI shows it as
  intentionally off, not broken).

### `/api/health` extension
Extend the existing public endpoint (`api.py:14`) to add a `sources` map:

```json
{
  "status": "ok",
  "db": true,
  "sources": {
    "nvd":    {"status": "ok",      "last_run": "...", "consecutive_failures": 0},
    "github": {"status": "error",   "last_run": "...", "consecutive_failures": 4},
    "news":   {"status": "skipped", "last_run": null,  "consecutive_failures": 0}
  }
}
```

Overall `status` degrades to `"degraded"` when any **enabled** source has
`consecutive_failures >= 3`. `db` failure still yields the existing hard
failure. Endpoint stays unauthenticated.

### Admin page (read-only)
New `/admin/sources` route, `@role_required("admin")`, reusing the blueprint
pattern in `horus/web/routes/admin.py`. Renders a `source_health` table:
source · status badge (green/yellow/red) · last run (relative) · last error ·
CVE/PoC counts. No toggles, no credential fields. Add a nav link in the admin
section.

### Files
- `horus/storage/schema.sql` — `source_health` table (idempotent CREATE)
- `horus/storage/db.py` — `upsert_source_health()`, `get_source_health()`
- `horus/pipeline.py` — try/except hook around `mod.run(ctx)`; record health
- `horus/web/routes/api.py` — extend `/health` with `sources` + degraded logic
- `horus/web/routes/admin.py` — `/admin/sources` view
- `horus/web/templates/admin_sources.html` — new template
- tests: `tests/storage/`, `tests/web/` (health JSON shape, admin page RBAC),
  `tests/test_pipeline*` (failure isolation + health recording)

### Acceptance
- A source raising inside `run()` records `error` + increments
  `consecutive_failures`, and the cycle completes other sources.
- `/api/health` returns per-source status; goes `degraded` at ≥3 failures of
  an enabled source.
- `/admin/sources` renders for admins, 403 for non-admins.

## 5. Workstream D — KEV due-dates (M3) + API docs

### 5.1 KEV due-date tracking (reused verbatim from v0.11 M3)
**Problem:** the CISA KEV feed carries a `dueDate` (federal remediation
deadline). Horus stores `kev=1` but discards the date.

**Design:**
- `enrichers/kev.py` captures `dueDate` into a new `cve.kev_due_date` column.
- Triage gains a KEV due-date lens (overdue first, then due-soon).
- New Telegram notification category: "KEV overdue / due-soon".

**Files:**
- `horus/enrichers/kev.py` — parse + store `dueDate`
- `horus/storage/db.py` + `schema.sql` — `kev_due_date` column
- `horus/web/routes/triage.py` + `templates/triage.html` — due-date lens
- `horus/notifications/dispatcher.py` + `format.py` — new category
- notification-preference seeding if categories are enumerated there
- `tests/enrichers/` KEV tests + `tests/test_notifications.py`

### 5.2 API documentation
New `docs/api.md` documenting the stable JSON API:
`/api/health` (incl. new `sources` map), `/api/stats`, `/api/cves`,
`/api/cve/<id>` (incl. `?year=`). Request params, response shape, auth
requirement, example responses. Closes issues.md OPEN-04.

### Acceptance
- KEV enrichment persists `kev_due_date`; triage lens orders overdue→due-soon;
  Telegram category dispatches.
- `docs/api.md` covers all four endpoints with example payloads.

## 7. Risks

| Risk | Likelihood | Impact | Mitigation |
|------|-----------|--------|------------|
| mypy strict on `web/` surfaces many errors | High | Low | Last in order; its own commit; can split per-route |
| Coverage stalls below 80% on hard-to-mock modules (xsearch/bot) | Medium | Low | Mock at the I/O boundary; gate only raised once met |
| Health hook changes pipeline failure semantics | Low | Medium | Preserve "continue on source error"; test failure isolation |
| KEV `dueDate` absent for non-KEV CVEs | Expected | None | Column nullable; lens filters to KEV rows |
```

# Horus v0.11 — Exposure & Prediction ("Prioritize") — Design Spec

> **Date:** 2026-06-24
> **Version target:** v0.11.0
> **Theme:** Stop treating all critical CVEs equally. Rank by real-world
> **exposure** + time-to-exploitation **imminence**, using data Horus already
> has plus an optional Shodan signal.

---

## 1. Design Philosophy

Horus today collects, enriches (KEV/EPSS), scores reputation, and delivers
(web + Telegram). It does **not** yet prioritize by *when* a CVE is likely to
be exploited or *how exposed* the affected products are in the wild. v0.11
closes that gap while preserving Horus's principles:

- **NVD remains authoritative.** New signals enrich; they never create CVEs.
- **Dependency-light.** The forecast is a transparent heuristic, not an ML
  model. Exposure is an *optional* enricher that no-ops without an API key.
- **Plugin model.** Exposure follows the existing `enrichers/*.enrich(ctx)`
  contract. No pipeline rewiring beyond the standard enricher hook.
- **ML-ready, not ML-now.** v0.11 logs the history and labeled outcomes a
  future model will train on, but ships zero ML code.

**Non-goals (v0.11):**
- No ML model (heuristic only; ML is v0.12, trained on v0.11's accrued data).
- No Censys adapter (interface is built; Shodan is the only adapter shipped).
- No new web framework / SPA. Jinja2 + vanilla JS + Chart.js as today.

---

## 2. Architecture

Four components, each independently shippable and each matching an existing
Horus pattern.

### 2.1 EPSS History + Velocity (M1)

**Problem:** `enrichers/epss.py` fetches a current EPSS score and overwrites
`cve.epss_score`. History is lost, so we can't see a *rising* EPSS — the
strongest pre-exploitation signal.

**Design:**
- New `epss_history(cve_id, score, recorded_at)` table.
- The EPSS enricher appends a history row whenever a CVE's score is fetched
  (idempotent per `(cve_id, recorded_at-date)` — at most one row per CVE per
  day to bound growth).
- `core/forecast.py::epss_velocity(cve_id, conn) -> float` computes
  Δscore/Δdays over the most recent two distinct history points (0.0 when
  fewer than two points exist).

**Files:**
- modify `horus/storage/db.py` — `epss_history` table DDL + migration
- modify `horus/enrichers/epss.py` — append history rows
- create `horus/core/forecast.py` — `epss_velocity()`
- create `tests/core/test_forecast.py`, extend `tests/enrichers/` EPSS tests

### 2.2 Imminence Forecast (M2)

**Problem:** the dashboard's "imminent" KPI is a naive `epss_score >= 0.5`
count (`horus/web/queries.py:250`). It ignores velocity, KEV, and PoC signal.

**Design:** `core/forecast.py::compute_imminence(cve, *, epss_velocity) ->
tuple[float, str]` returns `(score 0–10, bucket)` where
`bucket ∈ {imminent, weeks, months, unlikely}`.

Transparent weighted heuristic (exact weights tuned during implementation;
starting point):

```
imminence =
    EPSS_value        * 3.0        (0–3.0)
  + EPSS_velocity_norm* 2.0        (0–2.0)   # normalized rising-rate
  + KEV               * 2.0        (0 or 2.0)
  + PoC_signal        * 1.5        (0–1.5)   # count + freshness
  + CVSS/10           * 1.0        (0–1.0)
  + ubiquity_bonus    * 0.5        (0–0.5)
  cap 10.0

bucket: >=7.5 imminent | >=5.0 weeks | >=2.5 months | else unlikely
```

Stored on the CVE row as `imminence_score` (REAL) + `imminence_bucket` (TEXT),
recomputed each run after enrichment (alongside `compute_reputation_score`).

**Files:**
- modify `horus/core/forecast.py` — `compute_imminence()`
- modify `horus/core/merge.py` — call it where reputation is computed, OR a
  dedicated post-enrich pass in `pipeline.py` (decided in plan; must run
  *after* EPSS/KEV enrichers so velocity + kev are populated)
- modify `horus/storage/db.py` — `imminence_score`, `imminence_bucket` columns
- modify `horus/web/queries.py` — replace naive imminent count with bucket
  count; expose imminence in stats
- modify `horus/web/templates/dashboard.html` + `static/dashboard-charts.js` —
  imminence distribution chart, "Imminent" KPI
- extend `tests/core/test_forecast.py`

### 2.3 Exposure Enricher — Shodan-first, pluggable (M4)

**Problem:** Horus has no real-world exposure signal. A CVSS 7.0 on 50k
internet-exposed hosts outranks a CVSS 9.0 on 50.

**Design:** new optional enricher `enrichers/exposure.py` following the
`enrich(ctx)` contract, with an adapter interface so providers are swappable:

```python
class ExposureAdapter(Protocol):
    name: str
    def host_count(self, cve: CVE) -> int | None: ...   # None = unknown

class ShodanAdapter:
    # reads SHODAN_API_KEY; queries Shodan count API per affected
    # product/CPE or per CVE; returns exposed host count.
```

- `DEFAULT_ENABLED = True` but the enricher **no-ops cleanly** when
  `SHODAN_API_KEY` is unset (mirrors X-auth-absent behavior). Logs a single
  "exposure: no API key, skipping" line.
- Rate-limit aware: cap queries per run (config tunable), prioritize CVEs by
  reputation/imminence so the budget hits the CVEs that matter.
- Writes `cve.exposed_host_count` (latest) + `cve_exposure(cve_id, provider,
  host_count, recorded_at)` (history).

**Files:**
- create `horus/enrichers/exposure.py` — adapter Protocol + ShodanAdapter +
  `enrich(ctx)`
- modify `horus/storage/db.py` — `cve_exposure` table + `exposed_host_count`
  column
- modify `horus/config/tunables.py` — `EXPOSURE_MAX_QUERIES_PER_RUN`
- modify `horus/web/queries.py` + list/vendors templates — exposure column +
  sort key
- create `tests/enrichers/test_exposure.py` — mocked Shodan, plus the
  no-API-key no-op path

### 2.4 KEV Due-Date Tracking (M3)

**Problem:** the CISA KEV feed carries a `dueDate` (federal remediation
deadline). Horus stores `kev=1` but discards the date.

**Design:**
- `enrichers/kev.py` captures `dueDate` into a new `cve.kev_due_date` column.
- Triage gains a KEV due-date lens (overdue first, then due-soon).
- New Telegram notification category: "KEV overdue / due-soon".

**Files:**
- modify `horus/enrichers/kev.py` — parse + store `dueDate`
- modify `horus/storage/db.py` — `kev_due_date` column
- modify `horus/web/routes/triage.py` + `templates/triage.html` — due-date lens
- modify `horus/notifications/dispatcher.py` + `format.py` — new category
- modify `horus/storage/migrations` / `notification_pref` seeding if categories
  are enumerated there
- extend `tests/enrichers/` KEV tests + `tests/test_notifications.py`

### 2.5 ML-Ready Outcome Logging (M5)

**Problem:** a future ML forecast (v0.12) needs labeled training data:
"this CVE became KEV / got a PoC N days after publication."

**Design:** new `exploitation_outcome(cve_id, published_at, first_poc_at,
became_kev_at, first_exploited_signal_at, recorded_at)` table, populated/
updated each run from data already in the DB. **No model in v0.11** — this is
pure data accrual so v0.12 has history to train on.

**Files:**
- modify `horus/storage/db.py` — `exploitation_outcome` table
- create `horus/core/outcomes.py` — per-run upsert logic, called from pipeline
  end (or as part of the post-enrich pass)
- create `tests/core/test_outcomes.py`

## 3. Data Model Summary

| Change | Type | Purpose |
|--------|------|---------|
| `epss_history(cve_id, score, recorded_at)` | new table | velocity + ML training |
| `cve_exposure(cve_id, provider, host_count, recorded_at)` | new table | exposure over time |
| `exploitation_outcome(cve_id, published_at, first_poc_at, became_kev_at, first_exploited_signal_at, recorded_at)` | new table | ML labels for v0.12 |
| `cve.imminence_score` REAL | new column | heuristic forecast score |
| `cve.imminence_bucket` TEXT | new column | imminent/weeks/months/unlikely |
| `cve.exposed_host_count` INTEGER | new column | latest exposure |
| `cve.kev_due_date` TEXT | new column | CISA remediation deadline |

All additive; the existing idempotent column-migration path in `db.py` applies.

## 4. Web / Delivery Surface

- **Dashboard:** imminence distribution chart (Chart.js); "Imminent" KPI now
  counts `imminence_bucket = 'imminent'` instead of `epss >= 0.5`.
- **/cves and /vendors:** new sortable **imminence** and **exposure** columns.
- **Triage:** KEV due-date lens (overdue → due-soon → rest).
- **Telegram:** "imminent" and "KEV overdue" notification categories via the
  existing dispatcher; gated by `notification_pref` like other categories.

## 5. Milestones (sequenced, each independently shippable + tested)

| M | Title | External dep | Depends on |
|---|-------|--------------|------------|
| **M1** | EPSS history + velocity | none | — |
| **M2** | Imminence forecast + dashboard | none | M1 (velocity) |
| **M3** | KEV due-date tracking + triage lens + Telegram | none | — |
| **M4** | Exposure enricher (Shodan adapter, no-op without key) | Shodan key (optional) | — |
| **M5** | ML-ready outcome logging | none | — |

M1→M2 is the only hard ordering (M2's velocity input comes from M1). M3/M4/M5
are independent and can land in any order. Each milestone ends green:
`pytest` ≥ 70 % coverage, `ruff check` clean.

---

## 6. Roadmap Positioning

- **v0.11 (this spec)** — Prioritize: exposure + heuristic imminence.
- **v0.12** — Exposure depth (Censys adapter) + **ML forecast** trained on the
  `epss_history` + `exploitation_outcome` data v0.11 accrues, upgrading M2's
  heuristic in place behind the same `imminence_score` interface.
- **v0.13+** — the unbuilt differentiator themes not chosen for v0.11:
  Correlation & Verification (CVE chains, PoC verification, attack graphs),
  then Intel Publishing (STIX/TAXII, ATT&CK, Metasploit mapping), then the
  AI layer (NL query, LLM summaries, auto-triage).

---

## 7. Testing Strategy

- `core/forecast.py`: unit tests for `epss_velocity` (0/1/2+ history points)
  and `compute_imminence` bucket boundaries.
- `enrichers/exposure.py`: mocked Shodan adapter; explicit no-API-key no-op
  test; rate-limit budget test.
- `enrichers/epss.py` / `kev.py`: history append idempotency; `dueDate` parse.
- `core/outcomes.py`: upsert correctness across runs.
- Web: imminence/exposure columns render; dashboard `__DASHBOARD_DATA__`
  includes imminence buckets; triage due-date lens 200s.
- Telegram: new categories format + dispatch with mock API.

**Definition of done:** `pytest --cov=horus` ≥ 70 %, `ruff check` clean, all
new tables migrate idempotently, exposure enricher proven to no-op without a
key, and the dashboard "Imminent" KPI reflects the new bucket.

---

## 8. Out of Scope (v0.11)

- ML model / training pipeline (v0.12).
- Censys / non-Shodan exposure adapters (interface only).
- Correlation engine, STIX/TAXII, ATT&CK mapping, AI layer (v0.13+).
- Backfilling `epss_history` from outside Horus — history accrues forward
  from the first v0.11 run.
